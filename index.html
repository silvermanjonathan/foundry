Calling Foundry models from Python

One endpoint, one credential, many models. By the end of this module you can point the OpenAI Python SDK at a Microsoft Foundry resource, sign in with a key or with Microsoft Entra ID, and switch models by changing a single string.

What you will be able to do

  1. Explain what a deployment is and which settings it carries.
  2. Build the correct v1 base URL for any Foundry resource and say why it needs no api-version.
  3. Call a model from Python with an API key stored in an environment variable.
  4. Call the same model with keyless Microsoft Entra ID authentication, and explain why production code should prefer it.

Before you start

You need an Azure subscription, a Foundry resource with at least one model deployment, and Python 3 on your machine. For lesson 5 you also need the Azure CLI and a role assignment on the resource that lets you run inference. If you have no deployment yet, Microsoft's guide Add and configure model deployments walks through it. Lessons 1, 2, 6 and 8 work without any Azure access, so you can read ahead.

1

How Foundry organizes models

Goal: know what you are actually naming when you pass model=.

Foundry puts models from many providers behind a single endpoint that uses one set of credentials. Your code never talks to "DeepSeek" or "Llama" directly. It talks to your resource, and names a deployment.

A deployment is an alias. It gives a model a name you choose and attaches settings to it. Every deployment defines:

  • the model name and the model version,
  • a provisioning or capacity type,
  • a content filtering configuration,
  • a rate limiting configuration.

The last three vary with the model you choose. One resource can hold many deployments.

Deployment names here are illustrative. Yours are whatever you or your admin chose.

Two facts to keep

Billing follows use. You pay for inference run on a deployment, not for the deployment existing. Creating a second deployment to experiment costs nothing until you call it.

Deployments are Azure resources. That means Azure Policy applies to them, so an organization can govern what gets deployed the same way it governs any other Azure resource. If you are rolling AI out across a team, this is where guardrails live.

Predict: a teammate renames the deployment chat-main to chat-prod. What in your Python code must change?

Show answer

Only the string you pass as model. The base URL and the credential stay the same, because they point at the resource, not at a deployment. This is also why you can switch between models from different providers without rewriting code.

2

Anatomy of the endpoint

Goal: write the correct base_url from memory.

Every Azure OpenAI endpoint starts from the same base: https://<resource-name>.openai.azure.com. This endpoint exposes the full feature set of OpenAI models, including assistants, threads, files and batch inference, and it can also serve non-OpenAI models.

Two ways to reach a deployment

Per-deployment route

  • Append /deployments/<deployment-name> to the base URL.
  • Each deployment has its own URL.
  • You still use one authentication method across all of them.

v1 route (used in this module)

  • Call /openai/v1/ on the base URL.
  • Put the deployment name in the model field of each request.
  • Versioning is implicit, so you do not pass api-version.

The v1 route is what lets you use the plain OpenAI client class from the openai package. You give it a base_url and a credential, and it behaves as it would against any OpenAI-compatible API.

If you don't know your resource name, find it in the Azure portal or run az cognitiveservices account list.

Try it: build your client

Predict: which of these is a correct v1 base_url for a resource named contoso-ai?

  1. https://contoso-ai.openai.azure.com/openai/v1/?api-version=2024-10-21
  2. https://contoso-ai.openai.azure.com/openai/v1/
  3. https://contoso-ai.openai.azure.com/deployments/chat-main/openai/v1/
Show answer

B. A adds an api-version, which the v1 route doesn't take. C mixes the per-deployment route into the v1 URL. With v1, the deployment name travels in model, never in the path.

Set up Python

Goal: an isolated environment with the two packages this module uses.

You need the openai package for every call. You need azure-identity only for keyless authentication in lesson 5. Install both now so you don't have to come back.

The --upgrade flag matters. The v1 route and the Responses API rely on a recent SDK, and older virtual environments often carry an outdated openai version.

For lesson 5 only

Install the Azure CLI and run az login. On your own machine, that sign-in is what keyless authentication uses.

Call with an API key

Goal: a working first call, with the key kept out of your code.

An API key from your Foundry resource is the fastest way to a first response. Copy a key from your resource's keys page in the portal and put it in an environment variable called AZURE_INFERENCE_CREDENTIAL.

Now save this as first_call.py, replace the resource and deployment names, and run python first_call.py.

Line by line

line 2
You import the standard OpenAI class, not a special Azure class. The v1 route makes the resource look like any OpenAI-compatible API.
line 5
The base URL names your resource and ends in the /openai/v1/ route. There is no api-version anywhere.
line 6
The key comes from the environment, so it never lands in source control.
line 9
responses.create calls the Responses API, which carries the latest inference features.
line 10
The deployment name goes in model. Swap this string to use a different model.
line 14
output_text is a convenience property that gathers the text of the response into one string.

Why keys are convenient

  • Nothing to configure beyond copying a string.
  • Good for a quick experiment on your own resource.

Why keys are risky

  • A key grants full access to the resource.
  • You can't scope it to one person or one action.
  • You have to rotate it by hand.

Microsoft's guidance is direct: for production workloads, use keyless authentication. That is lesson 5.

Predict: you open a new terminal and run first_call.py without setting the variable again. What happens, and when?

Show answer

Python raises KeyError: 'AZURE_INFERENCE_CREDENTIAL' on line 6, before any network request is made. Environment variables set with export or $env: last only for that terminal session. The error is useful: it fails early and names exactly what is missing.

5

Call without a key

Goal: authenticate with Microsoft Entra ID and understand what each object does.

Foundry deployments support keyless authorization through Microsoft Entra ID. Instead of a shared secret, requests carry a short-lived token that proves who is calling. Access is tied to identities, which you can scope, audit and revoke.

Three steps

  1. Get access. Someone with rights on the resource configures it for Entra ID and grants your identity permission to run inference. Follow Configure keyless authentication with Microsoft Entra ID for the exact roles.
  2. Sign in. Run az login in your terminal.
  3. Swap the credential in your code. Everything else stays the same.

Line by line

line 2
Both helpers come from azure-identity.
line 4
get_bearer_token_provider wraps the credential in a function that returns a valid token when called, fetching a new one as needed. You never handle expiry yourself.
line 5
DefaultAzureCredential tries several sign-in sources in turn. On your laptop it typically finds your Azure CLI login. Running inside Azure with a managed identity, it finds that instead.
line 6
The scope https://ai.azure.com/.default says which service the token is for. A token for the wrong scope is rejected.
line 11
You pass the function as api_key, not a string. The SDK calls it to get a token for its requests.

Compare this file with first_call.py. The resource, the route, the deployment and the responses.create call are identical. Only the credential changed.

Predict: you deploy keyless_call.py unchanged to an Azure service that has a managed identity, and that identity has been granted inference access on the resource. What do you have to edit?

Show answer

Nothing. DefaultAzureCredential finds the managed identity at runtime, the same way it found your CLI login locally. No secret needs to be copied into the service's configuration. This is a big part of why keyless is the production default.

Responses and the fallback

Goal: know which API to call, and what to do when a model says no.

The examples so far use the Responses API. It works with Azure OpenAI models and with the Foundry Models sold by Azure that support it, such as DeepSeek, Llama and Grok models.

Not every deployment supports it. When one doesn't, the request fails with 400 Model not supported. The fix is to call the Chat Completions API through client.chat.completions.create on the same client. The request and the response are shaped differently:

Responses API

  • Send input=, a string.
  • Read response.output_text.

Chat Completions API

  • Send messages=, a list of role and content dictionaries.
  • Read completion.choices[0].message.content.

In both calls, model is still the deployment name. The client, base URL and credential don't change.

Predict: you call responses.create on a deployment that doesn't support it. Which Python exception does the openai SDK raise?

Show answer

openai.BadRequestError, the SDK's exception for HTTP 400. You'll catch it in the lab. Catch it narrowly: a 400 can also mean a malformed request, so check that the message is about the model not being supported before falling back.

Lab: a reusable client

Goal: one small module that combines everything, then use it to compare two models.

Work in the virtual environment from lesson 3. Try each task before opening the solution. Tick a task when your version runs.

Task A: a client factory that picks its own auth

Create foundry_client.py with a function make_client(). It reads the resource name from an environment variable (call it FOUNDRY_RESOURCE; the name is your choice, not an Azure convention). If AZURE_INFERENCE_CREDENTIAL is set, use the key. Otherwise use keyless authentication.

Show a solution

Importing azure.identity inside the function means a key-only setup works even if that package isn't installed.

Task B: ask, with a fallback

Add ask(client, deployment, prompt) to the same file. Try the Responses API first. If the model isn't supported, retry through Chat Completions. Any other error should still raise.

Show a solution

Line 9 re-raises any 400 that isn't about model support, so a real bug in your request isn't silently turned into a second call.

Task C: same prompt, two models, no code changes

Write compare.py that sends one prompt to every deployment in a list and prints each answer under its name. If you have only one deployment, create a second one first; it costs nothing until you call it.

Show a solution

This is the claim from lesson 1 made concrete: the models may come from different providers, and the only thing that differs between calls is a string.

Task D (stretch): report which API answered

Change ask to return a pair: the text, and either "responses" or "chat". Update compare.py to print it. Then run with the key unset and confirm keyless still works.

Show a hint

Return (response.output_text, "responses") from the try block and (completion.choices[0].message.content, "chat") after the fallback. In compare.py, unpack with text, api = ask(...). To test keyless, run unset AZURE_INFERENCE_CREDENTIAL (PowerShell: Remove-Item Env:AZURE_INFERENCE_CREDENTIAL).

Troubleshooting

Goal: read an error and know where to look first.

Most first-run failures come from a short list. The exception names in the first column are the ones the openai and azure-identity packages raise.

What you seeLikely causeWhat to check
KeyErrorThe environment variable isn't set in this terminal session.Set it again in the same terminal that runs Python.
AuthenticationError (401)The key is wrong or was rotated, or a token was issued for the wrong scope.Copy the key again. With keyless, confirm the scope is https://ai.azure.com/.default.
PermissionDeniedError (403)Your identity signed in but has no permission to run inference on this resource.Ask for the role assignment from the Entra ID guide. New assignments can take a few minutes to apply.
NotFoundError (404)The deployment name has a typo, or the base URL is missing /openai/v1/.Compare model with your deployment list, character by character. Check the end of base_url.
BadRequestError (400)
Model not supported		The deployment doesn't support the Responses API.Call client.chat.completions.create instead, or use ask from the lab.
CredentialUnavailableErrorDefaultAzureCredential found no usable sign-in.Run az login, then run your script from a new terminal.
APIConnectionErrorThe host name doesn't resolve, often because a full URL was pasted where only the resource name belongs.Make sure the base URL contains the resource name once, with no extra https:// inside it.

Predict: keyless worked yesterday. Today you get PermissionDeniedError but your colleague's identical script works. What is the first thing you check?

Show answer

Which identity you are signed in as. az account show tells you. A 403 means authentication succeeded and authorization failed, so the code and URL are fine; the question is whether this identity, in this tenant, still has its role on the resource.

Cheat sheet

Remember

  • A deployment is a named alias: model, version, capacity type, content filter, rate limit.
  • You pay for inference on deployments, not for having them.
  • Deployments are Azure resources, so Azure Policy applies.
  • v1 base URL: https://<resource>.openai.azure.com/openai/v1/, no api-version.
  • Deployment name goes in model.

Decide

  • Quick experiment on your own resource: API key in AZURE_INFERENCE_CREDENTIAL.
  • Anything shared or in production: keyless with DefaultAzureCredential.
  • Default to responses.create.
  • On 400 Model not supported: chat.completions.create.
